Why "Free" Usually Means "Limited"

Most free file transfer tools have a catch. Google Drive caps free storage at 15GB. WeTransfer's free tier maxes out at 2GB per transfer. iCloud gives you 5GB before it starts nagging. These services upload your file to someone else's server, store it there, then let the other device download it. That round trip through the cloud is the bottleneck, and it's also where the restrictions live.

I built OpenDrop because I got tired of emailing photos to myself just to get them from my iPhone 15 to my Windows PC. The core idea: if both devices are on the same network, why send files through a server in Virginia?

Direct device-to-device transfer skips the cloud entirely. Your file goes from phone to PC in one hop. No storage limits apply because there's no intermediate storage. The file lands directly in the receive folder on the destination machine. On macOS and Linux that's ~/Downloads/OpenDrop/Files, and on Windows it's %USERPROFILE%\Downloads\OpenDrop\Files.

But "direct" still has to deal with the physical reality of moving bytes across a network. The method matters enormously.

How Remote Transfers Work

When you transfer a file over HTTP, you're sending a request body from client to server. For small files (a few megabytes), you can stuff the whole thing into a single POST request. The server reads it, writes it to disk, sends back a 200. Done.

Large files break that model when there's a server in the middle that caps how big a single request can be. The fix isn't to chop the file into hundreds of little requests; it's to open one persistent connection and stream the bytes through it.

OpenDrop's remote transfers run over its own encrypted relay. On OpenDrop Pro the file streams straight through — the sending device's bytes flow to the relay and on to the receiver with minimal buffering, no breaking the file into HTTP chunks, and no per-request size ceiling. Free remote transfers first try a direct peer-to-peer link and otherwise fall back to our Oracle Cloud relay, sent in resumable 5 MB chunks either way. Either way there's no per-transfer size cap, and the relay only ever sees ciphertext, since the file is end-to-end encrypted before it leaves your device.

Tip

Remote transfers have no per-request size cap. You can send a 10GB file over the relay — Pro carries it in one streamed connection, the free tier in resumable 5 MB chunks. It just takes longer than LAN because the bytes travel over the internet instead of your local network.

The tradeoff is speed. Remote transfers travel over the public internet and through the relay rather than staying on your local network, so they're slower than LAN. Free transfers run on our Oracle Cloud relay (a smaller, always-free server, so it's the slower path); OpenDrop Pro adds a faster, dedicated Fly.io relay with automatic failover to Oracle if Fly is ever down.

That streaming model is a deliberate change from how OpenDrop used to work. Earlier versions tunneled remote transfers through a third-party service that capped HTTP request bodies, which forced the file into small chunks and capped throughput. Running our own relay removed that ceiling: there's no third-party request-size limit to design around, so Pro transfers stream end to end, and free transfers move in our own resumable 5 MB chunks by choice rather than being forced into tiny pieces by someone else's request cap — and there's nothing extra to download, nothing for antivirus or a firewall to flag.

LAN Streaming: The Fast Path Nobody Talks About

Remote transfers travel over the relay and the public internet. On a local network, none of that applies.

When your phone and PC are on the same WiFi, OpenDrop uses a completely different transfer path. The desktop app runs an HTTP server on port 8000. The mobile app discovers it via mDNS (the service type is _opendrop._tcp.local.) and connects directly. No relay, no cloud, no internet round-trip at all. Just your phone talking to your PC over your own router.

LAN transfers use streaming, the way file transfer should work. The phone opens a connection, starts writing the file data, and the server starts writing to disk as bytes arrive. No chunking, no reassembly, no per-piece overhead. The transfer speed is limited only by your WiFi hardware.

On my home network, I regularly move multi-gigabyte files between my iPhone 15 and my Windows desktop. WiFi 5 (802.11ac) gets roughly 100-300 MB/s depending on signal strength and interference, though real-world numbers depend heavily on your specific router and environment. The point is: LAN streaming is an order of magnitude faster than remote transfers over the relay.

Every user gets LAN streaming for free. No account required, no Pro upgrade needed. If both devices are on the same network, you get the fast path automatically. OpenDrop detects the connection type and picks the right transfer mode without you doing anything.

Remote Transfers Without a Tunnel: How the Relay Works

Remote transfers (different networks) are where things get interesting. Your phone on cellular in Greenville, SC, your PC on home WiFi. They can't discover each other via mDNS because they're not on the same broadcast domain.

OpenDrop solves this with its own high-speed relay. Both the desktop and mobile apps dial outward to the relay — there's no third-party tunnel binary to download, no public URL to share, and nothing for antivirus or a firewall to flag. Because the apps dial outbound, it works behind NAT and restrictive firewalls without any port forwarding. The file contents are end-to-end encrypted with ChaCha20-Poly1305 (RFC 8439 IETF AEAD) before they ever reach the relay, so the relay sees only ciphertext — it forwards opaque bytes and cannot decrypt them. TLS sits underneath as a second encryption layer.

There's no per-request size cap to work around. For someone sending a few photos or a document, it's quick. For someone moving 4GB of raw video footage, it goes through end to end — on Pro as one continuous stream, on the free tier in resumable 5 MB chunks — slower than LAN, but no longer bottlenecked by a third party's request limits.

A couple of things are worth knowing for the fastest experience:

  1. Get on the same network when you can. If you can connect both devices to the same WiFi (even a phone hotspot works), you skip the relay entirely and get full LAN streaming speed.
  2. Pro gets the faster relay. Free remote transfers run on our Oracle Cloud relay (sent in chunks); OpenDrop Pro adds a faster, dedicated Fly.io relay with automatic failover to Oracle that streams end to end without chunking. Neither tier imposes a per-transfer size cap.

The first one is worth knowing about. If I'm at my desk and need to pull files from my Redbeat D5 (my budget Android test phone), I just make sure both are on my home WiFi. The transfer mode switches automatically from relay to LAN.

Putting It Together: A Real Transfer from Phone to PC

Here's what actually happens when you send a 1.5GB video from an iPhone to a Windows PC using OpenDrop on the same network.

The desktop app starts its HTTP server on 0.0.0.0:8000. It registers the mDNS service (_opendrop._tcp.local.) so other devices can find it. The iPhone app scans for that service type using Bonjour (Apple's mDNS implementation) and finds the PC. You select the video file, tap send.

The app opens an HTTP connection to the PC's local IP on port 8000. Each request is signed with HMAC-SHA256 using a shared secret, with a timestamp window to prevent replay attacks. The file body itself is end-to-end encrypted with ChaCha20-Poly1305 (RFC 8439 IETF AEAD) before it leaves the phone, so even though the LAN carrier is plain HTTP, the bytes on the wire are ciphertext. The file streams as a single encrypted HTTP request body; the PC decrypts each frame as it arrives and writes plaintext to %USERPROFILE%\Downloads\OpenDrop\Files.

No chunk boundaries, no reassembly step, no cloud round-trip. The file appears on the PC as it's being received. Total time for 1.5GB over WiFi 5 varies by hardware but typically finishes in well under a minute.

Now consider the same transfer with both devices on different networks. The relay kicks in. On Pro that 1.5GB file streams as one continuous connection — phone → relay → PC — with no chunking; on the free Oracle relay it's sent in chunks. Either way there's no size cap. It's slower than LAN since the bytes travel over the internet, but it works from anywhere.

What OpenDrop Pro Adds (and When You Don't Need It)

Every remote transfer runs over OpenDrop's own relay. The free tier uses our Oracle Cloud relay; OpenDrop Pro adds a faster, dedicated Fly.io relay with automatic failover to a backup Oracle Cloud relay if Fly is ever down. Either way, the relay is a pass-through: bytes flow from phone to relay to PC with minimal buffering, as binary WebSocket frames.

The relay streams binary frames rather than base64-encoded JSON — we discovered base64 encoding added 33% overhead, so switching to binary frames meaningfully improved throughput. Pro's dedicated Fly.io relay is the faster path and streams the whole file; the free Oracle Cloud relay runs on a smaller, always-free server, so it's slower and sends the file in resumable 5 MB chunks, with no size cap on either.

You don't need Pro if your devices are usually on the same network. LAN streaming is already the fastest option, and every user gets it. Pro makes sense if you frequently transfer large files between locations, like pulling footage off your phone while traveling to your home workstation.

For most people, the free tier handles daily file transfers without issues. Share a photo album, move a presentation, send a batch of documents. The free Oracle Cloud relay isn't fast, but it's free, reliable, and has no hard file size ceiling. LAN transfers are fast and free. That combination covers the majority of file transfer needs without paying for anything.

OpenDrop is available on Windows, macOS, Linux, iOS, and Android. Download it, open it on two devices, and send something. On the same network, the transfer starts immediately.
